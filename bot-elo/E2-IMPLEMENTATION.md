# Gomoku Bot Elo E2 — Trusted Bot Match Execution (source only)

E2 uses the existing Gomoku app, THIEPN Account identity, Supabase \`gomoku-room\` Edge Function, existing online Renju legality checks, and **the exact native search kernel extracted from the original \`index.html#rules-engine\`**. It does not introduce a second rating engine, PvP writer or externally generated bot victory.

## What is actually implemented

- \`bot-matches.ts\` implements authenticated owner-only creation, active-match resume, exact server move/terminal validation, human move submission, bot responses, resignation, state reads and recent history.
- \`native-bot-engine.js\` mirrors the original Studio engine without altering its rules/search. Use \`python bot-elo/extract-native-engine.py\` after intentional native engine changes.
- The existing \`gomoku-room/index.ts\` router delegates only \`/api/bot-matches\` requests to the E2 handler; PvP actions/rankings are unchanged.
- Scoped \`gomoku_bot_matches\` schema migration stores owner-private game transcript, immutable bot configuration snapshot, server-selected seed, last command ID, revisions and verified result. It is intentionally **not applied** in this branch.
- \`bot-elo/trusted-play.js\` embeds a server-driven match view in the original app. No local bot search or game-result authority is used in this board. It calls the **existing** \`GomokuCompetitionBridge.accountPost/accountGet\`, respecting THIEPN Account linkage.
- The standalone \`index.html\` includes the E2 UI source; synchronize with \`python bot-elo/embed-e2.py\`.

## Endpoints (new E2 handlers; require deployed Edge Function and migration)

| Method | Route | Meaning |
|---|---|---|
| GET | \`/api/bot-matches/catalog\` | Provisional bot list (not rated) |
| POST | \`/api/bot-matches\` | Start, retry or resume one signed-in bot game |
| GET | \`/api/bot-matches/active\` | Resume current owner-private game |
| GET | \`/api/bot-matches/history\` | Recent owner-private verified results |
| GET | \`/api/bot-matches/:id\` | Read a match owned by the authenticated account |
| POST | \`/api/bot-matches/:id/action\` | Human move (or resign), followed by trusted bot search if needed |

Human actions include \`{commandId,revision,action:"move",i}\` or \`action:"resign"\`. Clients cannot supply a bot move, result, bot rating, winner, or settlement. The server locks the original bot level/config, rule and color at creation. All bot replies are generated by the original Studio search and independently validated against the already-established online rules. Each successful turn group commits through a revision-guarded compare-and-swap update. Request keys avoid duplicate games; there is one active game per account. Old/stale revisions fail and require a state refresh.

The source enforces the original center-first Renju practice opening, legal fouls, verified wins, draws, optional passes and resignation. There are no hints or takebacks in verified games. Results remain private to their owner and can be resumed from a second device.

## Explicit boundaries

- E2 matches are **verified training, not rated Bot Elo**. \`rated=false\` and \`ratingDelta=null\` everywhere. No additions to \`gomoku_ratings\`, \`gomoku_rating_events\`, tournament outcomes or Elo profiles. All E1 bot ratings remain **uncalibrated**.
- Server bot choices are selected by the canonical Studio search and recorded with server seed, search-budget snapshot, move and search metadata. The current search uses a wall-clock time budget, so *re-running the same position on different hardware is not guaranteed to reproduce the same move*. The stored, validated move transcript is reproducible and authoritative. A strictly deterministic search mode and/or equivalence protocol should precede real Elo rewards.
- E2's limited server search budgets and fixed balanced policy are **not** claimed to match the client-side humanization or to justify any Elo number. E3 must calibrate these exact deployed server policies, including openings and color.
- The E2 SQL file is source-only. Until its authorized migration and Edge Function deployment occur, the new UI reports backend unavailability and original local practice continues. No production change is implied.
- Actual fair-play policies, operational recovery, time controls and Elo settlement remain subsequent phases.
